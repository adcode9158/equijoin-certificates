# Frozen physical routing test

The test compares two per-query DuckDB buffer choices (32 and 128 MiB) for the ordered identifier-tuple ROW_NUMBER operation used in the earlier stress test. The previous 36 full-query low-memory outcomes are used only for calibration. The new test cohort contains no full-query cases and no subplan whose parent occurs in those 36 full cases. Cap for running the experiment: at most 3,000,000 output rows, 256 MiB temporary disk per execution, 12-second interrupt. Within each band (0–65,536; 65,537–262,144; 262,145–1,048,576; 1,048,577–3,000,000) select the first eight eligible cases sorted by SHA-256 of the string route-holdout-v1/CASE-ID. Use all available when fewer than eight qualify. Bands constrain experiment cost and ensure a spread of actual fanouts; the tested routing procedures never receive the band or recorded answer.

Calibrate a one-dimensional high-memory trigger on the 36 earlier full-query outcomes. Score = row count times (16 + 8 × number of joined tables). Predict high memory above the cut maximizing balanced spill-or-failure classification accuracy, i.e. mean sensitivity and specificity; ties favor fewer high grants. Use the identical calibration procedure separately for actual rows and for the engine's EXPLAIN join cardinality at the input to the window. Exact row-based routing uses the certificate executor with the implied integer row budget. It cannot see the actual count. Controls include the native optimizer estimate, always low, always high and a fully charged factorized joined-count SQL preflight making exactly the same choices as the certificate. Further compare with granting high memory to the top native estimates under exactly the certificate's tested number of high grants. The latter is an offline equal-allocation control; it does not see physical test outcomes.

Physically execute both grants per question in paired, order-balanced runs in two rounds. Connections are fresh and the input database read-only. Verify the window cardinality, completed counts and matching checksums. The main resource outcomes are failed or spilled executions, high grants and temporary bytes. Primary latency is total measured operator plus preflight wall time, and p95 uses the nearest-rank method. For a positive claim the certificate must reduce failures/spills at equal high grants against the native-ranking control without increasing charged total latency in either round, and the certificate must be cheaper to run than exact SQL preflight. Report any tradeoffs even when this criterion fails. Engine EXPLAIN used by the measurement harness for plan assertions is common and excluded from operator timing; the native policy pays for its own EXPLAIN. Separately charge C++ process start, resident-fixture import and first-use postings, and report the resident shared-engine boundary. No production SLA or concurrency is claimed.
